# Decisions

| ID | Date | Decision | Why | Rejected |
|---|---|---|---|---|
| D1 | 2026-11-08 | Rust core with language bindings as adapters over it; exact binding set undecided | One implementation, many hosts; keeps bindings free of logic | Per-language reimplementations |
| D2 | 2026-11-08 | Velopack is a reference only; lunepack-rs is a new design, not a 1:1 clone | Goal is a better design that avoids Velopack's mistakes | Porting Velopack's design and formats wholesale |
| D3 | 2026-11-08 | License is MIT OR Apache-2.0 (`LICENSE-MIT`, `LICENSE-APACHE`) | Rust ecosystem convention; user's choice | Single license |
| D4 | 2026-11-08 | Public GitHub repo `lune-rs/lunepack-rs`, `main` is the base branch | User's choice; first consumer is Lunegit | Private repo |
| D5 | 2026-11-08 | Primary API is Rust; other-language bindings are the last roadmap step (user, 2026-11-08) | Rust consumers come first; other languages later, so bindings are not near-term | Building a .NET (or other) binding early |
| D6 | 2026-11-08, revised 2026-11-12 | Own package and feed format v1 (`docs/FORMAT.md`): DSSE-signed JSON (`keys.json`, `root-<k>.json` for root rotation, one feed per channel listing every target, one manifest per release and target); a single `.pack` per release and target with one frame per file (a closed set: stored, LZMA2, BCJ x86 or ARM64 + LZMA2, BCJ2; D33); the manifest records each frame's own SHA-256 next to the file's; per-file `.delta` assets; target ids `<os>-<arch>` with fallbacks | Everything authoritative is signed, per-file Range fetch works, no per-OS channel matrix, and the frame hash is checked before any decoder sees a byte | A Velopack-compatible nupkg plus release feed (unsigned feed, re-zip after delta); a zip or tar.zst with a detached manifest (zip parser ambiguity, no tar random access); zstd frames (replaced by D33) |
| D7 | 2026-11-08 | Two-tier update trust: an offline root (threshold m-of-n, default 1-of-1, public part compiled into the app) signs a versioned key set that delegates to online release keys; release keys sign the feed (monotonic `seq`, optional `expires`) and manifests; clients keep the highest key-set version and feed seq seen (anti-rollback); a leaked release key is revoked by the root without an app update | A lost or leaked single key would otherwise need a new app build for every install | A single minisign-style key (no revocation path); full TUF (four roles, heavy for single-publisher apps) |
| D9 | 2026-11-13 | Linux packaging: lunepack's own tree install, per-user `~/.local/share/<app-id>` and per-machine `/opt/<app-id>`, done by the runtime installer; outputs are a GUI installer `<App>-<ver>-<target>-setup` (static runtime as bootstrap plus the signed payload) or the runtime's CLI, and a portable `.tar.xz`; XDG desktop entry and bin symlink; the runtime is a static musl binary. AppImage, deb and rpm come after v1 (self-update off when package-managed) | No glibc mismatch; one install model on every distribution; per-machine installs work | AppImage-first (weak per-machine story); deb or rpm plus a repo (updates belong to apt or dnf, repo signing); Flatpak and Snap (own updaters) |
| D10 | 2026-11-13 | macOS install and update: bundle swap. Stage on the same volume, verify, `RENAME_SWAP`, keep the old bundle for rollback, supervised relaunch. Scope is by ownership (a user-writable bundle is per-user, root-owned is per-machine); a translocated app is refused. Outputs: an installer app in an LZMA `.dmg` (built on a macOS host), a `.zip` of the bundle from any host, a `.pkg` for per-machine installs | Atomic swap with a rollback copy; no root for per-user installs | `installer -pkg` on every update (root every time, no rollback); versioned code inside a stable outer bundle (breaks the outer bundle's signature seal) |
| D11 | 2026-11-13 | Windows per-user layout: a stable stamped stub `<App>.exe` at the install root (the app's icon and VERSIONINFO via editpe, Authenticode-signed with the app's certificate) and immutable `app\<ver>\` directories; the active version is a pointer in the install state; shortcuts, the uninstall entry and PATH point at the stub; rollback re-points; old directories are deleted later with retries. Known cost: the real exe path changes per version, which matters for per-path firewall rules (documented; apps can add rules in hooks) | No directory renames under antivirus or file locks; clean rollback | Velopack-style `current\` renames; the app's own exe copied to the root (works only for Rust apps) |
| D12 | 2026-11-13 | Per-machine installs: one privileged apply engine with copy-then-verify behind thin OS triggers, so a standard user gets updates without a prompt per update. Windows: a LocalSystem service that Users may start; the pipe takes only an app id and files are read while impersonating the caller. macOS: a LaunchDaemon via SMAppService. Linux: a root systemd unit that a polkit rule lets local users start. An IT policy switch disables self-update on managed installs | No UAC, authorization or pkexec prompt per update; the install state is scope-aware from the start | Elevating on every update (standard users cannot update); IT-managed only (no self-update per-machine) |
| D13 | 2026-11-13 | Lifecycle hooks are declarative: shortcuts, file associations, URL schemes, autostart and PATH are declared in the manifest and performed by lunepack. App code runs as in-process callbacks at its next normal start (`on_installed`, `on_updated{from,to}`, `on_first_run`), with no relaunch and no kill timer. Optional hook executables only for install- and uninstall-time work, JSON over stdio with a declared timeout and progress lines | Apps are not killed mid-hook; the manifest says what an install does | Velopack-style relaunch with hook arguments, killed after a timeout |
| D14 | 2026-11-08 | In-app API is runtime-agnostic async (user's choice at the gate): the core stays synchronous and sans-IO; the facade's long operations are `async fn`s whose futures are `Send + 'static` and need no runtime, running blocking work on lunepack-owned worker threads; a `lunepack::blocking` wrapper serves apps without async; cancellation by dropping the future or a `CancelToken` | Works on tokio, smol or no executor, and shares one synchronous core with the runtime | Blocking-only API (the planner's recommendation); async-first on one runtime (forces it on others); a Cargo feature per runtime (breaks additive features, rule 5) |
| D16 | 2026-11-08 | Edition 2024; `rust-toolchain.toml` pins 1.99.1; `rust-version = "1.88"` (the floor the planned dependencies declare), checked in CI; the MSRV is bumped only in minor releases | Matches the format hook; a stable floor for downstream users | MSRV = latest stable; MSRV <= 1.85 by pinning old dependencies |
| D17 | 2026-11-08, revised 2026-11-12 | "Pure Rust" means: all first-party code is Rust, no external binaries for compression, deltas, hashing or update signing; the core and the verification path are pure Rust. Compression is pure Rust (`lzma-rust2`, Apache-2.0 only); zstd is not used unless D8 picks it. A dependency feature that adds unsafe code or asm is allowed only where this file names it and only in an adapter crate: today `lzma-rust2`'s default `optimization` feature in `lunepack-codec-lzma`, and `ring` via rustls in `lunepack-http` (the boundary rule for the first arrives in M3, so it is a decision, not yet enforced) (enforced from M3). The GPU and window stack (LuneUI, wgpu, winit, their OS crates, run-time loading of GPU drivers and display libraries) is to be confined to the UI adapter crate and the UI binary (D35); that confinement arrives with them. OS tools only where the OS mandates them (signtool, codesign, notarytool), through argv signers | Keeps the trusted path auditable without giving up compression ratio; the LZMA decoder only sees frames whose hash matched the signed manifest | A strictly pure-Rust dependency tree; vendored zstd (a C dependency) as the default codec |
| D18 | 2026-11-08 | CI and tests: a GitHub Actions 3-OS matrix on the public repo (disposable runners carry installer and per-machine tests) plus local Docker for Linux; pushes are batched at milestone ends; installer tests never touch the developer machine outside temp roots | Real OS behavior without risking a developer machine | Shared VMs over SSH (exclusive use, manual state reset) |
| D19 | 2026-11-13 | Runtime and UI binary provenance: in v1 the packager builds them from source for the target, or takes `--runtime <path>` and `--ui <path>`; prebuilt, signed binaries with hashes pinned in the CLI arrive with the release workflow. Packaging for another OS from one host therefore needs those paths until then | Needs no release infrastructure first; no cross-build of crates with C build scripts has been verified | Prebuilt only (needs release infrastructure first); source only (non-Rust apps need cross toolchains) |
| D20 | 2026-11-08 | Publishing in v1: the packager writes a self-contained release directory to upload with any tool to any static host; the upload order (packs, manifests, then feed) is documented; `lunepack publish` comes after v1 | Keeps cloud SDKs and credentials out of v1 | Upload adapters in v1 |
| D21 | 2026-11-08 | Crypto: Ed25519 (`verify_strict`), SHA-256, DSSE pre-authentication encoding with a payload type per document kind; algorithm ids in the format | Small, well-reviewed primitives; strict verification rejects malleable encodings | RSA or ECDSA (larger, more misuse-prone); BLAKE3 (less universal tooling); canonical-JSON signing (canonicalisation differentials) |
| D22 | 2026-11-08 | Install state is an append-only store of sequence-numbered, checksummed records; the reader takes the highest valid one; old records are pruned later | Crash-safe without relying on atomic rename semantics on every OS | A single file replaced by rename (not promised atomic on Windows) |
| D23 | 2026-11-08 | HTTP stack: `ureq` 3 on lunepack worker threads behind an object-safe async `Transport` trait, with the OS trust store (`rustls-platform-verifier`) and env proxies; Windows reads the user proxy (`win-system-proxy`); the macOS adapter reads the system proxy itself; the host app can inject its own `Transport`. Runtime behavior is checked by a CI probe before M4 relies on it; fallback is reqwest's blocking client behind the same trait | Corporate TLS-inspection roots and proxies work without configuration | reqwest async as default (forces tokio) |
| D24 | 2026-11-08 | No telemetry and no identifying query parameters; the staged-rollout bucket is derived from a local random install id and a release seed and is never sent | Privacy by construction | Velopack-style identifying query parameters |
| D25 | 2026-11-08 | Versions are SemVer 2.0; the packager rejects releases that differ only in build metadata; the client never downgrades automatically (rollback is local only) | Predictable ordering; no downgrade attacks | Automatic downgrades |
| D26 | 2026-11-08 | Crates and composition roots as in `docs/ARCHITECTURE.md`; the `lunepack` facade is the composition root for embedding apps and each binary has its own; the boundary check is a Rust xtask over `cargo metadata` plus real `toml` parsing that fails closed | Hand-parsed manifests keep missing forms that cargo accepts | A shell or awk checker |
| D27 | 2026-11-08 | Self-healing staging: files are staged one by one; a file failing its hash is re-fetched alone (Range) before the full-pack fallback; never an apply loop with nothing to download; direct deltas come from the last 3 releases; the packager round-trips every delta before publishing | No delta chains and no re-zip; failures repair themselves | Delta chains; a whole-package retry |
| D28 | 2026-11-08 | Each version ships its own runtime and a library only calls the runtime from its own build; the cross-version contracts are the state-record format and the Windows stub launch contract (plus the privileged-service protocol on machine installs) | No shared, frozen updater ABI to keep compatible forever | One shared updater called by any library version |
| D29 | 2026-11-08 | An optional local denylist scan runs before pushes (`./scripts/check-secrets.sh`, default config location `~/.config/lunepack-rs/denylist.txt`, outside the repo); CI skips it with a notice | A tripwire against committing private context to a public repo | Relying on review alone |
| D30 | 2026-11-12 | The boundary and denylist checks are subcommands of `xtask`; `scripts/*.sh` are thin bash 3.2 wrappers; shell tests (`scripts/tests/`) run in the gate, not in `cargo test` | One matcher for tree, paths and commits; `cargo test` stays free of gitleaks and jq on every OS | Bash/awk checkers; Rust tests that shell out to the scripts |
| D31 | 2026-11-12 | Workspace lints: `unsafe_code = "forbid"`, `unsafe_op_in_unsafe_fn = "deny"`, clippy `dbg_macro` and `todo` denied; `lunepack-fs` and the `lunepack-os-*` crates may lift `unsafe_code` and must then also deny `undocumented_unsafe_blocks` | Enforces rule 2's `// SAFETY:` comments | Pedantic clippy groups (noise on skeletons) |
| D32 | 2026-11-12 | `.gitattributes` sets `* text=auto eol=lf` | Bash scripts and rustfmt checks behave on Windows checkouts | Per-developer autocrlf |
| D33 | 2026-11-12 | Compression: each pack frame is one of a closed set: stored; LZMA2; BCJ x86 + LZMA2; BCJ ARM64 + LZMA2; BCJ2 (four sub-streams MAIN, CALL, JUMP, RC with per-stream lengths that `docs/FORMAT.md` fixes). The decoder checks the frame hash before decoding, takes the dictionary from the signed manifest (a power of two, at most 16 MiB, checked before any allocation) and requires the output length to match exactly. The packager picks the smallest candidate per file, stores a file when nothing is smaller, and round-trips every frame; the portable Linux archive is `.tar.xz`. Decoder speed of about 60 MB/s per core is accepted. A solid installer stream is not taken: it would add a second payload layout and verification path | Whole files are 10 to 22 percent smaller than zstd-19 in the research, BCJ2 about a further 6 percent on an x86 PE; one hardened frame layout everywhere | zstd frames; a solid installer stream |
| D34 | 2026-11-12 | The codec crate is `lunepack-codec-lzma` (renamed from `lunepack-codec-zstd`, M2). `lzma-rust2` is added to that crate only in M3, together with a boundary rule that no other package depends on it; until then that rule does not exist and nothing here is enforced. (enforced from M3) The crate keeps `unsafe_code = "forbid"` for its own code (the lint never reaches a dependency). CLAUDE.md hard rule 2 gains the sentence about dependency unsafe code and asm in the same M3 commit as the rule | Narrowest form of the documented exception that can be enforced; the doc never claims enforcement that does not exist | Keeping an empty `lunepack-codec-zstd` beside it; putting the codec crate on the `unsafe_code` allowlist (allows first-party unsafe and does nothing for the dependency) |
| D35 | 2026-11-12 | UI process model: the installer and update window are a separate UI process. Windows: Setup.exe is the stub as a UI-free bootstrap plus the payload. Linux: `<App>-<ver>-<target>-setup` is the static runtime as bootstrap plus the payload. macOS: an installer app whose main executable is the UI binary, with the runtime and payload in its Resources. No GPU or window stack runs in an elevated or privileged process, a UI fault cannot interrupt apply or rollback, and the Linux runtime stays static musl (the UI binary is glibc-dynamic and optional). Costs: a second binary per version and a same-build pipe protocol. Reversible until the UI ships | Keeps the privileged and supervising code small and free of GPU drivers | The UI inside the runtime (every elevated path carries the GPU stack); apps drawing their own update UI (no app runs during apply) |
| D39 | 2026-11-13 | LuneUI is taken as a git dependency pinned to a commit, with a boundary-check exception for exactly that source (planned for the UI milestone; no exception exists yet). Consequence: lunepack's UI crates stay `publish = false` and can never be published to crates.io, and building the UI from source needs a git checkout of lunepack. Gaps found in LuneUI are filed in its repository | LuneUI is not on crates.io; a git pin works without waiting for a release | A crates.io release first (the recommended option); a vendored snapshot under `vendor/` |
| M2-D1 | 2026-11-12 | Core dependencies: `lunepack-core` may depend on `serde` (derive), `serde_json`, `base64`, `semver`, `unicode-normalization` and `thiserror`, listed in `CORE_EXTERNAL_ALLOWLIST` of the boundary check, which fails any other external crate in core. Hex and the DSSE pre-authentication encoding are hand-written | Pure parsing and encoding crates only; hashing, signatures, clock and decoding stay behind core traits | A hand-written JSON parser (more to fuzz than serde_json's); the `url` crate (references are restricted relative paths, M2-D6) |
| M2-D2 | 2026-11-12 | Strict JSON: every document and envelope passes a pre-pass over the same bytes that rejects a repeated key at any depth (unknown keys included), nesting beyond 32, invalid UTF-8, a byte-order mark, trailing data and a non-object top level; only then serde's derive parses the typed body. Integers only, each at most 2^53-1. Unknown non-critical fields are ignored; envelopes deny unknown fields | serde's derive keeps the last of a repeated known key and ignores repeated unknown ones, which would be a parser differential | Parsing to `serde_json::Value` first (last-wins hides duplicates) |
| M2-D3 | 2026-11-12 | Root rotation is separate documents: root version k>1 is `root-<k>.json`, an envelope signed by root k-1's threshold and by root k's own threshold. A client walks k+1, k+2, ... from its trusted root and only then checks `keys.json`. A bad `root-<k>.json` fails the whole update check | Signature before parse forbids learning the signing root from inside the payload it signs | Rotations embedded in `keys.json` (circular); full TUF |
| M2-D4 | 2026-11-12 | Key ids: `id` is the lowercase hex SHA-256 of the 32-byte Ed25519 public key; documents carry both and verification recomputes the id. The envelope `keyid` is required and only selects a key; the threshold counts distinct verified keys; an unknown key id is skipped, a malformed one fails | One identity per key; duplicate or unknown ids cannot inflate a count | DSSE's optional `keyid` |
| M2-D5 | 2026-11-12 | base64 in envelopes (`payload`, `sig`) is the standard alphabet with canonical padding only. Deliberately stricter than DSSE, which makes verifiers accept either alphabet | One accepted encoding per byte string; lunepack's own writer is the only producer | Also accepting the URL-safe alphabet |
| M2-D6 | 2026-11-12 | Feed entries reference manifests (and later packs and deltas) by restricted relative paths: the shared path validator plus ASCII `[A-Za-z0-9._+-]` per component; no scheme, query, fragment or percent sign. Resolving a reference to a URL belongs to the transport | No reference can name another host or smuggle a query | Absolute URLs in the feed |
| M2-D7 | 2026-11-12 | Times and numbers: times are integer Unix seconds, `seq` an integer, all at most 2^53-1. Expiry and key windows read only the `Clock` trait. An implausible clock (`now` earlier than the installed release manifest's `issued`) skips expiry and key-window checks, and the verified value reports the skip. Expiry means `now >= expires` | Deterministic tests and replays; a wrong system clock must not make every update fail forever | Reading the system clock in the core |
| M2-D8 | 2026-11-12 | Fuzz entry points are `lunepack_core::fuzz`, a `#[doc(hidden)]` module of `fn(&[u8])` harnesses that run the real parsers and verification chain and drop the result; its fake hasher and signature scheme are private to the module | Fuzzing needs no public API that parses without verifying and returns typed values | A public parse-without-verify API |
| M2-D9 | 2026-11-12 | The fuzz project `fuzz/` is outside the workspace (root `exclude`) with its own committed `Cargo.lock`. The boundary check fails the build when `fuzz/Cargo.toml` exists without a lock or without the `exclude` entry, when a lock package is neither crates.io nor a workspace member by name and version, and when a fuzz dependency is git, from another registry, `workspace = true`, or a path that is not a workspace member. It is not in the gate (libFuzzer needs nightly and a C++ build); the gate replays the committed seeds and random inputs on stable | libFuzzer's build would otherwise enter the gate and the MSRV job; the fuzz lock is still held to the supply-chain rule | A workspace member |
